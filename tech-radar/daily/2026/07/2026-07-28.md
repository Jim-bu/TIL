## 🔵 Tech → Product (기술에서 서비스로)

**KodeKloud "K8s 관리 에이전트"(AIOps 패턴) → Robynn AI("자가치유 웹사이트")**

KodeKloud의 오늘 글들(*K8s를 관리하는 AI 에이전트 / LangChain+kubectl 트러블슈팅 / 플랫폼 엔지니어링용 멀티 에이전트*)은 하나의 패턴을 보여준다 — **관측 → 진단 → (승인 후) 자동 조치**의 자율 운영 루프.

이 AIOps 루프를 특정 도메인으로 좁혀 상용화하면 **Robynn AI**("스스로 개선·치유되는 웹사이트")가 된다. 사이트 지표를 관측 → 문제·기회 진단 → 자동 실험(A/B·밴딧)으로 개선하는 것. 즉 *인프라 자율 운영 패턴 → 웹사이트 자율 최적화 제품*. KodeKloud의 에이전트-운영 아키텍처(툴 정의·가드레일·승인)를 보면, Robynn류 자가치유 제품의 안전한 자동화 구조가 그려진다.

## 🟢 Product → Tech (서비스에서 기술로)

**Artifacts by Databox("AI 애널리스트→리포트") → 시맨틱 레이어 + 텍스트→SQL + 거버넌스 접근**

**Artifacts**는 "물으면 공유용 리포트를 돌려준다". 역으로 뜯으면: ① 자연어 질문 → ② **시맨틱 레이어**(지표·차원 정의)로 해석 → ③ **텍스트→SQL/쿼리** 생성·실행 → ④ 차트·리포트 조립. 진짜 난도는 ②③ — 아무 컬럼이나 긁는 게 아니라 *정의된 지표* 위에서만 안전하게 질의(거버넌스된 데이터 접근).

이 "시맨틱 레이어"는 이번 주 반복된 키워드다(Google Gemini·Microsoft Foundry의 semantic layer, 07-21 데이터 컨텍스트). 즉 에이전트가 조직 데이터를 다루려면 *스키마 위 시맨틱 레이어 + 권한/거버넌스* 가 전제. Artifacts를 이해하려면 텍스트→SQL과 시맨틱 레이어(dbt metrics류) 구현을 보면 된다.

## 🔬 Enterprise Deep Dive — Kubernetes 트러블슈팅/운영 AI 에이전트 (LangChain + kubectl, 가드레일 필수)

> 오늘의 1 Pick. 에이전트가 인프라를 "운영"하기 시작하는 첫 실전 — on-call 피로·MTTR를 줄이되, 파괴적 명령을 어떻게 막느냐가 급소.

### 왜 쓰나 (도입 근거)
- **해결 문제**: 장애 대응(on-call)은 반복·피로가 크고 MTTR가 길다. 에이전트가 *알럿 → 로그/상태 수집 → 원인 가설 → (승인 후) 조치* 를 도와 1차 트리아지를 자동화.
- **대안 대비**: *룰 기반 런북 자동화*(경직, 새 장애 못 잡음) ↔ *LLM 에이전트*(유연, 대신 환각·위험). 핵심은 **read-only 우선 + write는 승인**.
- **도입 효과**: 1차 진단 자동화로 MTTR·야근↓, 지식 표준화(런북의 살아있는 버전).
- **비용/리스크**: 환각으로 **파괴적 kubectl**, 과다 RBAC, 관측 부재 시 오진.

### 어떻게 연동하나 (기술 통합)
- **스택 위치**: `알럿(Prometheus/OTel)` → `에이전트(LangChain)` → `read-only 툴(kubectl get/describe/logs)` → *가설/조치안* → `승인 게이트` → *승인 시* `제한된 write`.
- **최소 통합(개념 예시)**:
```python
# 읽기 전용 툴만 우선 노출 (write는 별도 승인 경로)
tools = [
  Tool("kubectl_get",      run=lambda a: sh(f"kubectl get {a} -o json")),
  Tool("kubectl_describe", run=lambda a: sh(f"kubectl describe {a}")),
  Tool("kubectl_logs",     run=lambda a: sh(f"kubectl logs {a} --tail=200")),
]
# 위험 동사 차단(07-13 destructive_command_guard / 07-23 authz 패턴)
DENY = ("delete","drain","cordon","apply","edit","scale","patch")
```
- **운영 고려**: 에이전트 서비스어카운트는 **최소권한(RBAC, 기본 read-only)**, write는 사람 승인 후 별도 채널. 컨텍스트는 OTel/Prometheus(졸업한 표준)에서. 멀티 에이전트(triage/diagnose/remediate)로 역할 분리(KodeKloud 패턴).
- **함정(gotchas)**: ① 환각 파괴 명령 → default-deny 동사 필터 + 최소권한, ② 관측 데이터 없으면 오진 → 관측 선행, ③ 대형 클러스터 토큰 비용, ④ 프롬프트 인젝션(로그 내 악성 문자열).

### 도입 판단 체크리스트
- [ ] on-call/트러블슈팅 **반복 피로**가 큰가?
- [ ] **관측(OTel/Prometheus)** 데이터가 이미 있는가?
- [ ] **read-only부터** 시작할 수 있는가(write는 승인)?
- [ ] 에이전트 **RBAC 최소권한·위험명령 차단**을 걸 수 있는가?

→ 2개 이상 Yes면 *read-only 진단 에이전트*부터 도입. write 자동화는 가드레일(승인+최소권한+동사 차단)이 선 다음.
