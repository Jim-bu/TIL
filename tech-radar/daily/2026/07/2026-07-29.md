## 🔵 Tech → Product (기술에서 서비스로)

**huggingface/speech-to-speech(로컬 음성 에이전트) → Cekura·Leaping AI(상용 음성 에이전트)**

`speech-to-speech`는 오픈모델로 **STT→LLM→TTS** 로컬 파이프라인을 구성해 음성 에이전트를 만든다. 저지연 스트리밍이 핵심.

이 음성 스택 위에 상용 레이어를 얹으면 **Leaping AI**(전화·문자 캠페인 에이전트)나 **Cekura**(음성 에이전트 자가개선 루프)가 된다. 특히 Cekura가 중요한데, "만든다"에서 끝내지 않고 **통화를 평가 → 자동 개선**하는 루프를 붙였다. 즉 *음성 파이프라인(오픈소스) → 평가·개선 루프를 얹은 제품*. speech-to-speech의 파이프라인 코드를 보면, 이런 제품의 하부(지연·턴테이킹)와 그 위에 왜 평가 루프가 필요한지가 보인다.

## 🟢 Product → Tech (서비스에서 기술로)

**Prefactor("에이전트 실시간 평가") → OTel 트레이싱 + LLM-as-judge + 가드레일 메트릭**

**Prefactor**는 "AI 에이전트를 실시간 평가"한다. 역으로 뜯으면: ① 에이전트 실행을 **OTel `gen_ai` 스팬**으로 계측(입력·툴콜·출력), ② 실트래픽을 샘플링해 **evaluator**(LLM-as-judge, 규칙 체크, 포맷/툴콜 성공률)로 채점, ③ **회귀·가드레일 위반**을 대시보드/알럿으로. 오프라인(골든셋) + 온라인(실트래픽)의 결합.

토대가 오늘 CNCF의 **OTel 졸업** — 표준 관측 데이터가 있어야 평가가 가능하다. 즉 Prefactor 같은 제품은 *관측(OTel) + 평가(judge/규칙) + 회귀 게이트* 의 조합. Microsoft Foundry의 eval 툴, 07-16의 OTel `gen_ai.*` 계측과 같은 계보다.

## 🟣 Tech → Business (기술에서 비즈니스로)

**모델 상품화 → "증명 가능한 신뢰성(Eval)"이 새 구매 기준이자 계약 산출물**

어제 모델이 반값이 됐고, 오늘은 **"그럼 얼마나 믿을 수 있나"를 측정·보증하는 도구**(Prefactor·Cekura·Foundry eval·ECC)가 몰려나왔다. 방향은 분명하다 — 모델이 흔해질수록 구매 결정은 **성능이 아니라 신뢰성의 증거**(eval 점수·회귀 게이트·SLA)로 넘어간다.

여기에 KodeKloud의 **ArgoCD로 모델을 GitOps 배포**(선언형·감사가능)가 더해지면, "에이전트 품질"은 *반복 배포 + 지속 평가* 의 운영 문제로 성숙한다. 솔루션 벤더 시사점: **eval 리포트 + GitOps 배포 이력**이 엔터프라이즈 조달의 신뢰 근거가 된다. 즉 "우리 모델이 좋다"가 아니라 **"우리는 품질을 측정하고, 회귀를 막고, 재현가능하게 배포한다"** 가 세일즈·계약의 언어가 된다.

## 🔬 Enterprise Deep Dive — 에이전트 평가(Eval) 파이프라인 in CI & 프로덕션

> 오늘의 1 Pick. **검수·납품의 언어**. "이 에이전트가 얼마나 정확·일관적인가"를 수치로 증명하고, 변경 때마다 회귀를 막는다.

### 왜 쓰나 (도입 근거)
- **해결 문제**: 프롬프트·모델·데이터가 바뀔 때마다 품질이 **몰래 퇴행**한다. 수동 스팟체크는 확장 불가. 납품·SLA엔 "정확도/일관성"의 수치 근거가 필요.
- **대안 대비**: *수동 검수*(주관적·비확장) ↔ *자동 eval 스위트*(오프라인 골든셋 + 온라인 실트래픽 평가). 
- **도입 효과**: 검수 객관화(점수로 합격/불합격), 회귀 조기 차단, 고객 신뢰(리포트 제출).
- **비용/리스크**: judge 편향·비용, eval 게이밍(테스트 과적합), 트레이스 내 PII.

### 어떻게 연동하나 (기술 통합)
- **스택 위치**: `오프라인` — 골든 데이터셋 → evaluator → **CI 게이트**(점수 하락 시 빌드 실패). `온라인` — OTel `gen_ai` 스팬 → 샘플 평가 + 가드레일 모니터.
- **최소 통합(개념 예시)**:
```python
cases = load_golden("acceptance.jsonl")  # 입력 + 기대 기준(정답/포맷/툴콜)
def evaluate(agent):
    scores = []
    for c in cases:
        out = agent.run(c.input)
        scores.append(judge(out, c.rubric))     # LLM-as-judge or 규칙 체크
    return mean(scores)
assert evaluate(agent) >= THRESHOLD, "검수 임계 미달 — 배포 차단"  # CI 게이트
```
- **운영 고려**: 골든셋은 실제 고객 시나리오로 구성·버전관리, judge는 소형·저비용 모델+규칙 병행, 온라인은 OTel(07-16)에서 샘플링, PII 마스킹.
- **함정(gotchas)**: ① judge 일관성(같은 답에 다른 점수) → 규칙+judge 병행, ② 골든셋 과적합(현실 괴리), ③ 데이터 드리프트로 점수 무의미화, ④ 평가 비용 폭증.

### 도입 판단 체크리스트
- [ ] 에이전트가 **프로덕션/고객 대상**인가?
- [ ] 프롬프트·모델 변경으로 **회귀 위험**이 있는가?
- [ ] **납품/검수·SLA**에 품질 수치 근거가 필요한가?
- [ ] **관측(OTel)** 또는 트레이스 수집이 가능한가?

→ 2개 이상 Yes면 *골든셋 + CI eval 게이트*부터. 온라인 평가는 OTel 계측 다음. **검수 기준 자체를 eval 케이스로 문서화**하면 납품 산출물이 된다.

## 💡 Deep Dive — 오늘의 인사이트

- **🧠 주요 개념** — *Eval-Driven Agents.* "reliability, not capability"의 실천 도구 — 실시간 평가(Prefactor)·자가개선 루프(Cekura)·회귀 게이트. 관측 표준(OTel 졸업)이 토대.
- **📦 주목 프로덕트** — *Prefactor / Cekura.* 에이전트를 *만드는* 게 아니라 **측정·개선**하는 카테고리의 부상 = 시장이 빌드에서 운영·품질로 이동했다는 증거.
- **🎯 핵심 기획력** — *"품질을 증명한다"를 판다.* 모델이 흔해진 시대에 eval·자가개선을 전면에 세워, 복제 어려운 **신뢰**를 상품화.
- **💼 Tech → Business** — 구매 기준이 성능 → **증명 가능한 신뢰성(eval 점수·회귀 게이트·GitOps 배포 이력)**. eval 리포트가 조달 신뢰 근거이자 계약 산출물이 된다.
- **한 줄 종합:** 어제 "모델은 상품이 됐다"에 대한 오늘의 답 — **"그럼 신뢰성을 측정·보증하라."** 가치가 모델에서 *평가·운영·재현가능 배포* 로 넘어가며, 이는 곧 **검수·납품의 언어**다.
