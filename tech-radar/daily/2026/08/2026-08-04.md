## 🔵 Tech → Product (기술에서 서비스로)

**firecrawl/pdf-inspector(고속 문서 추출) → 문서/OCR 기반 AI 제품(RAG·문서 에이전트)**

`pdf-inspector`는 PDF를 **분류(디지털 텍스트 vs 스캔 이미지)** 하고 텍스트·레이아웃을 **고속(Rust)** 으로 추출한다. 지저분한 문서를 깨끗한 구조로 바꾸는 인제스트 계층.

이 계층 위에 상용을 얹으면 **문서 기반 AI 제품**(계약·매뉴얼·리포트를 이해하는 RAG·에이전트)이 된다. 07-21에서 봤듯 **에이전트 답 품질 = 검색·추출 품질** 이므로, 이 인제스트가 곧 제품 품질의 하한선이다. pdf-inspector 같은 추출기의 분류·레이아웃 처리 코드를 보면, "문서를 이해하는 AI"가 왜 모델보다 **전처리(추출) 파이프라인**에 승부를 거는지가 보인다. (→ Deep Dive로 확장.)

**AgentSky**는 "원하는 하네스·모델로 클라우드 에이전트를 즉석 호스팅"한다. 역으로 뜯으면: ① 요청 시 **격리 실행 환경 프로비저닝**(07-23 box/microVM), ② 하네스·모델을 갈아끼우는 **추상화**(07-29 aisuite·OmniRoute), ③ 세션 간 **메모리**(오늘 TencentDB-Agent-Memory), ④ 액션 **인가·관측**(Kastra·OTel).

## 🟣 Tech → Business (기술에서 비즈니스로)

**에이전트 스프롤 → "거버넌스된 재사용 빌딩블록 플랫폼"이 해자**

The New Stack의 진단: 에이전트가 조직에 난립(sprawl)하면, 플랫폼 엔지니어의 새 일은 **거버넌스된 셀프서브 빌딩블록**(골든패스)을 제공해 이를 통제하는 것. 오늘 트렌드가 그 부품들이다 — **재사용 메모리 자산**(TencentDB-Agent-Memory), **온디맨드 런타임**(AgentSky), **표준 추출 라이브러리**(pdf-inspector).

방향: 가치가 *개별 에이전트*에서 **재사용·거버넌스되는 플랫폼 부품**으로 이동한다. 게다가 Qwen3.8-Max처럼 모델은 계속 쏟아져 상품화되니, 해자는 더욱 **부품·플랫폼**에 쏠린다. 솔루션 벤더 시사점: 고객마다 일회성으로 만들지 말고, **재사용 가능한 표준 블록(문서 추출·메모리·배포 템플릿)** 으로 패키징하면 딜리버리가 확장되고 마진이 는다. (이게 곧 PM의 "제안 표준화·재사용 자산화" 과제.)

## 🔬 Enterprise Deep Dive — 문서 인제스트 파이프라인 (PDF → 구조화 → 메모리/RAG)

> 오늘의 1 Pick. **OCR/문서 솔루션의 심장.** 에이전트·RAG의 답 품질은 이 추출 파이프라인이 결정한다.

### 왜 쓰나 (도입 근거)
- **해결 문제**: 계약·매뉴얼·양식 같은 **지저분한 PDF**(스캔·표·다단·헤더/푸터)를 순진하게 텍스트로 뽑으면 레이아웃이 깨지고, 에이전트는 **환각·오답**을 낸다(07-21 retrieval, 07-29 eval). 문서가 많은 엔터프라이즈엔 이 인제스트가 곧 품질의 하한선.
- **대안 대비**: *순진한 text 추출*(레이아웃 무시) ↔ *분류 + 레이아웃 인식 추출*(디지털/스캔 구분 → 스캔은 OCR, 표·다단 보존).
- **도입 효과**: 검색·응답 품질↑, 환각↓, 검수(eval) 통과율↑ — 문서형 솔루션의 핵심 경쟁력.
- **비용/리스크**: 스캔 오인식, 표/다단 붕괴, 대용량 처리 비용, 문서 내 PII.

### 어떻게 연동하나 (기술 통합)
- **스택 위치**: `PDF/이미지` → **분류**(디지털 vs 스캔) → **추출**(pdf-inspector류 고속 텍스트/레이아웃 · 스캔은 OCR 엔진) → **청킹**(레이아웃·의미 단위) → **임베딩/메모리**(cognee·Tencent memory) → **에이전트 그라운딩** → 품질은 **eval**(07-29)로 측정.
- **최소 통합(개념 예시)**:
```python
kind = classify(pdf)                       # digital-text vs scanned-image
text = extract_text(pdf) if kind=="digital" else ocr(pdf)  # 스캔은 OCR
blocks = layout_chunk(text)                # 표·다단·문단 보존 청킹
index.upsert(embed(blocks), meta={"doc": pdf.id})  # 메모리/RAG 저장
# 회수 품질은 골든셋으로 eval → 임계 미달 시 파이프라인 수정
```
- **운영 고려**: 스캔·표는 별도 처리(레이아웃/테이블 추출), 헤더·푸터 노이즈 제거, 데이터 사내 보관(온프렘·자체호스팅, 07-20), PII 마스킹, 대용량은 배치·큐(KEDA, 08-03).
- **함정(gotchas)**: ① 스캔 PDF를 디지털로 오인 → 빈 텍스트, ② 표/다단 붕괴로 의미 유실, ③ 잘못된 청킹으로 검색 실패, ④ OCR 오탈자 전파.

### 도입 판단 체크리스트
- [ ] 입력이 **PDF/스캔 문서** 위주인가?
- [ ] **스캔·표·다단**이 섞여 있는가(단순 텍스트가 아닌가)?
- [ ] 추출·검색 **품질을 eval**로 측정하는가?
- [ ] 문서를 **사내 보관**해야 하는가(규제)?

→ 2개 이상 Yes면 *분류 → (텍스트/OCR) 추출 → 레이아웃 청킹 → eval* 파이프라인부터. **모델을 키우기 전에 추출을 고치는 게** 품질 개선의 지름길.
